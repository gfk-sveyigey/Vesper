# 技术架构约定

## 依赖边界

- KSPlayer 负责媒体解复用、解码、渲染及其提供的播放控制能力；应用层不复制或私改其内部播放实现来承载产品逻辑。
- Vesper 负责媒体来源与元数据、播放流程、用户偏好、历史/收藏（若纳入首版）、错误转译和应用界面。
- UI 不直接承担网络协议解析或文件存储规则。通过明确的模型和服务边界连接界面与数据/播放能力。
- 上游 API 应通过 Vesper 自己的适配边界接入，避免 KSPlayer 类型扩散到所有业务模块。确需暴露时，应有明确理由。

## 建议职责分层

- **Presentation**：页面、视图状态、用户操作和可访问性。
- **Application**：用例编排，例如打开媒体、恢复进度、切换来源及偏好应用。
- **Media**：KSPlayer 适配、播放会话、播放状态映射和播放器事件。
- **Library / Sources**：本地与在线媒体来源的发现、描述和访问；具体协议按决策逐步加入。
- **Source Selection**：记录已配置来源及当前选中的来源标识；媒体页以该选择作为查询上下文，不将来源切换实现为主导航切换。
- **Persistence**：用户设置、收藏和播放进度等本地持久化；同步能力不默认包含。

这是职责约定，不要求在代码很少时先建大量空模块。目录和 target 划分应由实际依赖方向与构建需求决定。

## 媒体来源与播放契约

- 将媒体身份、显示元数据和播放地址/访问参数区分建模；不要把 URL 字符串当作完整的媒体模型。
- 本地资源的权限/访问句柄应明确生命周期，避免只保存可能过期的临时路径。
- 在线资源需处理加载、缓冲、鉴权/访问失败、网络中断和取消；敏感 header、token 不写入日志。
- 播放会话应能报告状态、进度、错误和可用轨道。应用层据此更新 UI，不以 UI 推测内核状态。
- 重试、恢复进度和自动选择轨道等行为应受用户偏好控制，并为不同来源定义合理默认值。

## 播放呈现与 PiP

- 播放会话与其呈现容器分离。全屏视图、应用内标题/导航区域紧凑播放条和系统 PiP 共享一个播放会话；呈现切换不得创建第二个播放器或重置播放状态。
- 播放呈现状态由应用层统一管理，至少区分全屏、紧凑播放、PiP 和已关闭/停止。切换应可取消且幂等，避免快速连续操作导致多个呈现同时持有播放视图。
- 不实现应用内可拖动浮窗。系统 PiP 使用目标 OS/播放后端支持的 Apple API，由系统管理浮窗生命周期。
- PiP 的暂停、继续及跳转命令应通过所选后端和系统媒体控制通道映射到当前播放会话。只发布当前媒体实际支持的命令；进度、播放状态和 Now Playing 信息保持一致。
- KSPlayer 不同后端的 PiP 能力可能不同。集成前必须针对所选后端、视频渲染层及目标 iOS 版本制作验证样例；若无法支持所需 PiP，则记录限制并调整后端/范围，不以自绘浮窗冒充系统 PiP。

## 并发、错误与资源

- 遵循项目采用的 Swift Concurrency 模型；跨 actor 边界的数据应满足隔离和 Sendable 要求。
- 播放会话创建、切换和销毁应有单一所有者，避免旧任务回调覆盖新会话状态。
- 使用结构化取消管理加载和搜索任务；切换媒体或退出时及时取消不再需要的工作。
- 将底层错误映射为稳定的应用错误类别，同时保留调试上下文；用户可见信息不得泄漏本地路径、认证信息或原始堆栈。

## 上游与许可管理

- 固定 KSPlayer 的版本/commit，不直接跟随不受控的上游变化。
- 升级依赖时检查 API/行为变化、平台支持、构建产物和许可条件，并记录升级理由。
- 上游 KSPlayer README 当前声明默认 GPL，并说明商业授权选项。引入前由项目负责人核实该版本、所选组件和分发方式的许可义务；许可问题未确认前，不作商业分发承诺。
