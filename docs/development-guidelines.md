# 开发准则

## 通用要求

- 优先使用当前 Swift/Xcode 工具链和仓库已确立的模式；在基础设施确定前，不提前引入大型依赖或复杂抽象。
- 保持变更聚焦。对外可见行为、数据契约和依赖版本变化应在 PR/变更说明中写明。
- 命名表达领域含义，避免无必要缩写；公共 API 和非显然的并发/生命周期约束需有简洁文档。
- 不提交密钥、用户数据、真实媒体凭据或带敏感参数的 URL。日志采用脱敏数据。
- 错误需可诊断且可恢复；不要用 `try!`、强制解包或空 `catch` 隐藏可预期失败。

## Swift 约定

- 使用明确访问控制，默认限制实现细节暴露范围。
- 视图保持轻量，状态变更和副作用放在合适的 model/use-case/service 中。
- 避免共享可变全局状态；需要共享状态时说明所有权、隔离方式和生命周期。
- 异步 API 提供取消语义；避免无必要的 `Task.detached`，并明确 UI 更新所在的 actor。
- 仅在提高理解或维护性时添加注释；注释解释原因、约束或非显然行为，不复述代码。

## 测试与质量门槛

- 新增业务逻辑应覆盖关键正常路径、边界和错误路径；缺陷修复应增加能复现问题的回归测试。
- 媒体播放集成测试应使用可公开分发的测试素材或 mock，不依赖私人 URL、账户或不稳定的外部服务。
- 对播放状态映射、恢复进度、资源权限和取消竞态等边界优先编写单元测试；必要时补充设备/模拟器集成测试。
- 提交前运行仓库实际支持的 build、test、lint/format 检查，并在变更说明中报告未运行项及原因。
- UI 改动验证空、加载、失败、长文本、动态字体和横竖屏等相关状态；不能只验证理想截图。

## 依赖与变更流程

- 新增依赖需说明解决的问题、维护状态、平台支持、许可和替代方案。
- KSPlayer 升级需检查 release notes、目标平台构建、播放回归和许可影响。
- 避免在一次变更中混入无关格式化或重构，以便审查行为差异。
- 设计/架构决策发生变化时，同步更新 `docs/` 中对应规范和待决项。

## 代码审查检查项

- 是否保持 UI、业务流程、媒体适配和持久化边界清晰？
- 是否覆盖取消、重复触发、切换资源和过期回调等异步场景？
- 是否正确处理本地资源访问与在线鉴权/网络错误？
- 是否泄漏凭据、路径或不必要的个人数据？
- 是否有相应测试、可访问性和错误状态反馈？

## 日志准则

- 统一使用 `AppLog` / Apple Unified Logging；按 lifecycle、navigation、sources、media、playback、services 分类，不散落 `print`。
- 保持单条日志简洁，以稳定事件名记录状态变化、失败原因和必要的耗时/关联标识；需要详尽诊断时增加结构化上下文，不重复打印同一错误。
- 默认记录关键生命周期与状态转换；Debug 补充详细诊断。未来高频进度、缓冲、重试事件应节流/汇总，不逐帧输出。
- 错误输出 domain/code 等可诊断信息，禁止直接输出包含 URL、路径或凭据的 localizedDescription/userInfo。敏感上下文标为 private；token、密码、认证 header 和完整媒体 URL 即便在 Debug 也不得记录。
- 排查跨流程问题时使用非敏感关联标识；未来日志导出需用户主动触发并再次脱敏，不自动上传。首版日志由系统保留，不维护额外无界文件。
- Git 开发与验证均在 `dev` 分支进行，只推送到远端 `dev`；不推送工作区临时分支，不自动合并或发布。

- 本地辅助/校验脚本不提交到 GitHub；构建使用仓库内的原生工程和现有 Actions 工作流。
